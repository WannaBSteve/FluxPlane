# 技术调研与选型依据

调研日期：2026-11-09。采用官方技术文档，并结合已有实现的定向阅读。本文区分文档可支持的能力与本项目的设计选择。

## 1. 连接器与增量接入

**Airbyte：Incremental Sync — Append**

官方说明围绕游标识别增量；同一记录的更新可能形成新增记录，合并去重与变更语义需要额外处理。文档还说明 schema 变化的限制。

对本项目的启示：连接器必须声明游标、主键、更新与删除能力。不能给所有来源统一贴上“增量同步”就认为语义完整。

选择：首版实现文件、PostgreSQL、SQLite、HTTP 和文档的有限连接器合同，不把完整连接器平台作为必需部署组件。

来源：https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/incremental-append

**Debezium：PostgreSQL connector**

官方文档描述快照、逻辑解码、增删改事件、位点和故障恢复；故障期间可能出现重复事件，消费者可以结合 LSN 等信息识别重复。

对本项目的启示：同步和执行应当允许重投递，通过幂等提交维持可见结果正确性。日志级 CDC 涉及源库配置与运维，不宜隐含在首版普通数据库接入中。

选择：保留 ChangeBatch 接口，首版采用满足条件的游标增量及快照对账，后续接入 CDC。

来源：https://debezium.io/documentation/reference/stable/connectors/postgresql.html

## 2. 依赖驱动更新与持久化调度

**Dagster：Declarative Automation**

官方定义是根据资产及其依赖的状态启动执行。它支持用自动化条件描述何时需要重新物化。

对本项目的启示：刷新需求应该来源于依赖变化、新鲜度与定义变化，而不仅是固定定时任务。

选择：在特征定义中表达刷新条件，planner 据此生成更新 DAG。首版自行实现受限任务模型，使交互查询、后台更新和版本发布使用同一套资源与状态规则；不同时维护两套独立编排器。

来源：https://docs.dagster.io/guides/automate/declarative-automation

**Temporal：Temporal Service / Server**

官方架构区分任务队列、工作进程、历史与匹配服务，适合需要持久执行历史和恢复的工作流。

对本项目的启示：业务任务与单次执行尝试分离；进程退出不应丢失任务状态。

选择：首版任务短、类型受限，以 PostgreSQL 队列和租约实现所需恢复语义。若引入跨天业务流程、复杂外部副作用或大量工作流分支，再评估 Temporal，避免长期自行扩展通用工作流引擎。

来源：https://docs.temporal.io/temporal-service/temporal-server

**PostgreSQL：SELECT locking clauses**

官方文档明确，`SKIP LOCKED` 跳过被锁记录，提供不一致视图，适用于多个消费者访问队列表的场景，不适用于通用一致性读取。

选择：仅用于任务领取，结合短事务、租约代次和唯一约束；发布使用事务条件更新，数据查询使用固定版本。

来源：https://www.postgresql.org/docs/current/sql-select.html

## 3. 特征定义与时间语义

**Feast：Feature views**

官方说明将特征组织为有来源、schema 和时间信息的逻辑集合，并区分在线与历史读取。该页特别说明非时间戳数据的适用限制。

对本项目的启示：衍生特征需要声明实体、输入、定义版本和时间语义。数据画像和运行画像不能直接等同于在线机器学习特征。

选择：首版定义较小的 FeatureDefinition 与 FeatureSnapshot 模型，明确窗口、迟到数据、定义版本和输入版本。需要专门的在线特征检索与训练时点一致性时，通过适配器集成特征平台，不提前承诺完整特征平台能力。

来源：https://docs.feast.dev/getting-started/concepts/feature-view

## 4. 数据交换与执行

**Apache Arrow：Columnar format**

官方规范定义语言无关的列式内存数据结构、元数据与序列化协议。

选择：连接器和执行器之间采用 Arrow 批次，持久数据采用 Parquet，队列中传递引用与清单。这样可以避免大型数据反复转成 Python 字典和 API JSON。具体路径是否零拷贝取决于实现，不作为普遍性能承诺。

来源：https://arrow.apache.org/docs/format/Columnar.html

**DuckDB：并发与嵌入式执行边界**

本轮官网请求出现页面正文未提取及访问拒绝，未据此完成当前版本并发功能的全文核验。已有实现展示了线程内计算、独立连接和版本化对象组织的用法；这不能直接推导多进程共享写安全。

选择：本项目采用保守而清晰的部署方式：每个计算进程有独立上下文，读取不可变数据文件；元数据和队列放 PostgreSQL。M0 固定精确依赖版本并验证实际需要的连接行为，避免依赖未核实的并发扩展。

官方入口：https://duckdb.org/docs/stable/connect/concurrency

## 5. 可观测性

**OpenTelemetry：Signals**

官方文档区分 traces、metrics 和 logs 等观测信号。

选择：请求、任务、同步和刷新共用关联标识；指标用于趋势与调度反馈，数据库中的任务和版本状态决定正确性。首版提供指标端点和结构化日志，完整遥测后端作为可选部署。

来源：https://opentelemetry.io/docs/concepts/signals/

## 6. 现有基础的阅读结论

本轮定向检查了接入、文档提取、查询特征、运行适配、资源准入、版本状态和后台发布相关实现。发现：

- 数据接入和执行具有可抽取基础，但混有运行脚本、特定数据集与路径约定。
- 已有后台准备和轻量发布机制，可以借鉴其职责分离。
- 部分版本管理明确限于单进程，不能直接作为新系统的跨进程状态管理。
- 普通 Python 子进程主要提供超时与进程边界，不构成执行不受信任代码的安全隔离。
- 调度、资源准入和候选处理已有局部能力，但尚不能据本轮阅读确认存在完整的持久化平台。

因此采用“能力抽取、接口重构、状态主干新建”的路径。本轮没有运行旧测试、验证吞吐量或审计所有调用路径；这些阅读结论仅用于规划迁移方式。

## 7. 选型决策汇总

| 决策 | 当前采用 | 延后采用的触发条件 |
|---|---|---|
| 接入 | 受限连接器合同 | 需要大量标准连接器时评估 Airbyte 集成 |
| 变更捕获 | 游标增量 + 快照对账 | 需要可靠捕获硬删除和低延迟变更时接 Debezium |
| 编排 | PostgreSQL 任务状态 + 调度器 | 跨天复杂工作流和外部副作用增多时评估 Temporal |
| 特征 | 版本化定义与快照 | 需要训练时点一致性和在线检索体系时评估 Feast |
| 数据执行 | DuckDB + Arrow + Parquet | 单机容量或并发不足时增加远程执行器 |
| 事件 | PostgreSQL 持久事件 + 唤醒通知 | 消费者和事件吞吐增长到实测瓶颈时评估消息系统 |
| 部署 | 单机 Compose | 多节点、故障转移或租户隔离要求出现时扩展 |

各项延后均保留接口，不将“可扩展”表述成已完成的兼容性。
